# OIC-6 v1.0 — quota, budget, reservation and reconciliation protocol

**Owner:** OIC admission/accounting service, invoked by every server-side provider dispatch, including evaluation. Browser and product callers cannot submit authoritative usage. Scope is immutable `(applicationId, tenantId?, principalId, resource binding ID)` after current runtime authorization. A quota limits resource units; a budget caps economic spend or OIU for an operation/campaign. Both may apply, and each applicable hard bucket must pass in one transaction. Soft buckets warn but never authorize an otherwise denied call.

## Bucket and policy resolution

`QuotaPolicyRevision` specifies exact dimension/unit, scoped subject (`SYSTEM|APPLICATION|TENANT|MODEL|TIER|CAPABILITY`), window (`LIFETIME|UTC_DAY|UTC_MONTH|ROLLING|CONTRACT_PERIOD`), limit, hard/soft, reservation upper bound, unknown-liability rule and effective interval. UTC calendar windows are half-open; contract period pins timezone and tzdb revision, converted once to UTC. Rolling windows use a defined duration and a transactionally maintained ring/expiring-post projection; implementation may choose a simpler exact query for v1 but cannot approximate hard limits. Reset opens a new bucket; rollover is disabled unless explicit revision. Include all matching hard policies, rather than choosing only a narrowest single policy; explicit deny beats grant. `BudgetRevision` has amount/currency or OIU unit, purpose, campaign/experiment owner and deadline; currency budget cannot be checked against unknown FX/cost as zero. Price estimate upper bound must be conservative; if no enforceable upper bound exists, admission is denied or restricted to a known bounded mode.

**Reservation sizing rule:** for each policy dimension, reserve `max(known fixed request cost, enforceable server-side upper bound from input already counted + output/tool/step ceilings × pinned worst applicable conversion/rate)`, plus explicitly published safety margin. The resulting bound and derivation are stored per leg. If provider billing can add an unbounded dimension or price cannot be bounded under a hard currency budget, deny that mode before dispatch. Existing input consumption is included, not charged twice. At UTC window boundary, a call reserves in the window where admission occurs and remains pinned there; new calls use the new window. Rolling-window projection expires entries only when their event-time semantics and watermark are settled; late usage posts an explicit historical adjustment and may create debt in the old bucket. A reservation lease expiry is **not** a release: `HELD` without a persisted attempt may be fenced/released after proof, while `DISPATCHED|UNCERTAIN` retains liability until provider settlement or approved conservative write-off with audited rationale. Automatic reset never forgives unknown liability.

`Admission` has UUID, unique `(scope, operation, idempotencyKey)`, request hash, pinned policy/plan/binding revisions, dispatch deadline and state. `Reservation` has UUID, one or more `ReservationLeg`s per bucket with exact decimal quantity and `expiresAt`, fenced lease generation and state `HELD|DISPATCHED|SETTLING|SETTLED|UNCERTAIN|RELEASED`. `ProviderAttempt` is created *before* outbound call, with unique physical attempt key, provider request key if available and trace. `UsageEvent` and postings use unique source attempt+receipt sequence; duplicate callback with identical digest is replay, different digest is a conflict/quarantine.

## Atomic sequence

1. Authenticate/authorize, resolve current binding and published rules, compute server-enforceable maximum from output cap and known unit/rate ceilings. The request hash includes scope, target, limits and policy revisions; a replay gets prior result, a changed replay conflicts.
2. In PostgreSQL serializable transaction, lock all matching bucket rows in stable key order; create missing rows under unique constraint; check `consumed + held + proposed <= hard limit` for each leg and budget; insert Admission/Reservation/RESERVE postings/outbox and update projections atomically. Serialization conflict retries boundedly, then returns `ADMISSION_BUSY`; DB failure denies dispatch.
3. Before provider network I/O, commit `ProviderAttempt` with reservation ID and fence; transition `HELD→DISPATCHED` atomically. A crash between reserve and attempt can safely release after lease proof; a crash after dispatch is uncertain until provider evidence. Never hold a DB transaction across network I/O.
4. On authoritative or provider-reported receipt, upsert immutable UsageEvent by source key. In one transaction post `CONSUME` and `RELEASE` difference to every affected bucket, update projections and state. A provider-reported unit beyond reservation posts full observed amount plus explicit overrun liability; it does not truncate truth. Unknown dimensions keep the relevant leg `UNCERTAIN` and hold a conservative liability cap.
5. Reconciliation worker compares receipt/invoice/attempt evidence. An operator-approved correction appends `ADJUST` or `REVERSE` referencing original posting and source evidence; projection changes in same transaction. `RECONCILED` records the process outcome, not an extra economic charge. Release an uncertain hold only with proof call did not dispatch or a settled provider accounting result. Expired time alone is insufficient.

**Crash boundary matrix:** pre-reserve: no provider call; post-reserve/pre-attempt: fenced release after deadline; post-attempt/pre-send: network ambiguity treated uncertain unless transport proves no dispatch; post-send/pre-receipt: liability hold/reconcile; post-receipt/pre-post: replay receipt via unique key; post-post/pre-ack: read committed result; after plan change: prior pinned rule governs existing hold. Stream chunks may produce incremental receipts, but current runtime streaming has no idempotency; production activation requires a new stable stream invocation/attempt protocol, monotonic sequence, disconnect settlement and no unaccounted retry. Until then hard quota can deny streaming or restrict it to bounded single-attempt behavior without replay.

**Concurrency and abuse:** no cache counter is authoritative. Lock ordering avoids deadlock; contention backoff is bounded and observable. A tenant cannot borrow another tenant's allowance. Reservation renewals require matching fence and still-live provider attempt; a stale worker cannot finalize. Rate limits guard API abuse separately from quota. A high-volume tenant can hot-spot its bucket; partition by scope/window only if exactly equivalent, else throttle. Quota reads expose `used`, `held`, `uncertain`, `remaining`, `window`, `asOf` and revision, with unknown cost/usage distinct. No future prediction from snapshot.

**Commands/queries:** `Admit`, `MarkAttemptDispatched`, `RecordUsageReceipt`, `Settle`, `OpenReconciliation`, `ApproveAdjustment`, `PublishPolicy`, `AssignPlan`, `CreateOverride`; each returns operation ID and committed readback revision, has command-specific scope/permission, idempotency key and audit. Read APIs are cursor-bounded by scope/time and show posting chain and evidence level; only privileged operators see commercial data. `EXHAUSTED`, `NOT_ENTITLED`, `UNKNOWN_PRICE`, `UNCERTAIN_USAGE`, `STALE_POLICY`, `CONFLICT`, `ADMISSION_BUSY` remain separate codes. Recovery workers and reconciliation are server-only.

**Test invariants:** property-test posting conservation and projection rebuild, rounding/order independence, unique replay, negative/overflow rejection and policy precedence. Run concurrent serializable admissions, duplicate callback, partial provider failure, network timeout, provider overrun, plan revision during call, unknown FX, DB crash at each numbered boundary, long lease, cancellation and invoice mismatch. Rollout shadow→canary→hard gate requires measured accounting coverage, zero unexplained projection drift and documented unknown-liability runbook; never silently revert to unmetered dispatch after hard gate activation.
