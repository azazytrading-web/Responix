# OIC-7 v1.0 — contextual Model DNA, Evolution Lab and promotion

## DNA is a measured capability envelope

The frozen X1 UI has 13 named DNA dimensions but no measurements. `DnaTraitDefinitionRevision` owns each dimension's construct, eligible domains/slices, metric/report inputs, unit and raw scale, polarity/target range, aggregation and uncertainty method, minimum effective n, coverage, freshness horizon and disqualifying safety/contamination states. A trait can be ratio, duration, cost, categorical band or calibrated index; **no universal 0–100 is forced**. `DnaMeasurement` pins `(target fingerprint, trait definition revision, benchmark release, cohort/context, report IDs, scope, evaluatedAt)` plus raw value/interval, evidence strength (`STRONG|MODERATE|WEAK`), availability (`MEASURED|PARTIAL|INSUFFICIENT|STALE|CONTAMINATED|UNSUPPORTED|REDACTED`) and method. Only `MEASURED` plus sufficient evidence can drive an asserted trait. Weak/partial may be displayed with label but never promoted to full measurement. Context-specific performance is not a global property of an edition.

**Projection rule:** `DnaMeasurement` is a deterministic materialized read projection over immutable eligible Measurement/Report IDs. There is no edit-score command. Rebuild with the same trait/method/input digests must yield the same output; changing trait definition, report eligibility, release or source availability creates a new projection revision with `supersedesId` and reason. The former projection remains historical. Projection keys include `targetClass`, target fingerprint and context. `BASE_MODEL`, model+domain, model+profile, binding and runtime-policy results occupy distinct keys and cannot be merged unless a published aggregation method explicitly defines a cross-context estimate with uncertainty. A model identity alone is insufficient. A changed provider/harness or stale report cannot silently refresh prior DNA.

Capability envelope is a set of contextual measured traits and coverage constraints, not one scalar. It may show domain/task/language, operating limits, provider/binding and temporal window. A trait derived solely from model judge is explicitly judge-based; configuration/profile intensity is never measurement. Drift detection compares same trait definition, benchmark anchor and target under current method, with uncertainty; a changed provider or release triggers new baseline. The X1 radar may render a polygon only for comparable measured traits on a validated common scale; otherwise show table/gaps and do not connect missing to zero. API returns source report IDs and availability per dimension. Review/retire trait definition via immutable revision, never silently recompute old display.

## Evolution Lab and target types

`CandidateRevision` is an immutable one-change-or-declared-change-set delta from an existing model revision/profile revision/binding. Candidate types: model instructions/specification, profile revision, binding/variant selection, context/retrieval/tool policy under currently supported OIC contracts, and explicitly versioned combination. No model weights/fine-tuning is implied. Parent lineage is a DAG with stable UUIDs, cycle prohibition and immutable ancestor links; fork/merge requires declared parent set and conflict resolution. An experiment pins baseline/challenger, target scope, treatment variable, benchmark release, primary/critical metrics, sample/stopping policy, OIC-6 budget and rollback target before dispatch. Practice/dev evaluation may iterate; protected promotion holdout is limited and separated from candidate generator. `Benchmark replay` is a new run with pinned release; `rescore` is new metric lineage over unchanged artifacts; `regrade` is a correction path with original preserved; none rewrites prior report.

Candidate state: `DRAFT→VALIDATED→EVALUATING→REVIEWABLE→APPROVED→PROMOTING→PROMOTED→MONITORING→VERIFIED`, with terminal `REJECTED|EXPIRED|ROLLED_BACK|UNVERIFIED`. Validation checks scope/lineage and published target revision. Reviewable requires successful report and OIC-6 budget settlement; approval pins human actors, candidate/report/verdict/policy digests and expiration. A `PromotionVerdict` may be `PASS|FAIL|INCONCLUSIVE|STALE|CONTAMINATED`; only `PASS` is eligible, and it expires when source target/binding/report/release/policy changes or explicit TTL elapses. Different evaluation costs/unknown economics are displayed; hard budget gate may reject unknown.

**Gate order:** authorization and two-person separation for high-risk scope → candidate lineage/current pointer check → fully comparable baseline/challenger reports → minimum sample, interval and multiplicity → all critical safety/privacy/language slices → quality practical gain or approved noninferiority → cost/OIU/latency guardrails → holdout integrity → OIC-6 settlement → fresh signed-by-service verdict digest. Human approval cannot turn an invalid verdict into pass. Champion/challenger exists per `(application, tenant?, environment, binding scope)`; no universal champion or global rank. Production promotion is a single privileged OIC-7 command with idempotency key, expected binding version, candidate/revision IDs and verdict digest. DB transaction inserts decision/audit and CAS binding pointer. If no row changed, return stale conflict; never retry against a different winner. Readback verifies pointer and decision. Canary traffic percentage is in a revisioned routing policy, not a silent variant mutation. Expansion requires post-promotion evidence and authorization. Rollback is a new CAS command to retained prior revision with reason/audit, not history deletion. An interrupted promotion is resolved by idempotent readback.

**Promotion UI:** canonical X1 controls for lineage, condition diff, benchmark pack/release, slice comparison, uncertainty, cost coverage, verdict reasons, approval, canary and rollback; no fake scores. **Security:** evaluator cannot grant promotion; OIC-8 cannot call promotion directly; human approver cannot edit holdout/metric after seeing candidate result. **Operations:** verdict expiry, orphan decisions, binding/readback mismatch, canary guardrail breach and missing post-promotion telemetry alert. **Tests:** cycle detection, stale binding, changed metric/judge release, low n, contaminated holdout, unknown cost, unauthorized scope, double-approve, concurrent promotions, acknowledgement loss and rollback drill. **Rollout:** evaluation-only candidates, then manual nonproduction promotion, then scoped canary with owner gate; advanced automated search and auto-promotion remain future extensions.
