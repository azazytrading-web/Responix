# OIC-6 — accountable usage and atomic control

> **HISTORICAL / DIRECTIONAL PREDECESSOR - NOT ACTIVE IMPLEMENTATION AUTHORITY.** The owner-approved OIC-6 through OIC-9 v1.0 lock in [the canonical OIC-6 to OIC-9 architecture](../../oic-6-9/00_MASTER_ARCHITECTURE_LOCK_MANIFEST.md) supersedes this material for implementation. Retained for historical context; do not use to override the locked package.


**Purpose:** answer who may consume which scoped resource, under which revisioned rule, how much was authorized/used, what the provider reported, what it cost, and what remains unsettled. Runtime remains the call owner; OIC-6 owns admission and accounting. No reliance on OIC-7/8.

## Proposed durable model

`PlanRevision` is an immutable entitlement/quota bundle; `PlanAssignment` is effective-dated for app/tenant; `EntitlementRevision` is a rule with action/resource/scope; `QuotaPolicyRevision` specifies dimension, hard/soft limit, UTC window, reservation ceiling and unknown-usage response. `UsageEvent` stores normalized and raw provider dimensions with attempt identity and source provenance. `UsagePosting` is append-only, decimal, typed `RESERVE|CONSUME|RELEASE|ADJUST|REVERSE`, with group ID and unique source/event key. `QuotaBalance` is a transactionally updated projection, rebuildable from postings, keyed by scope+policy revision+window. `PricingRevision` is immutable effective-dated source schedule; a posting also pins selected rate components and currency. `CostAssessment` stores estimated, provider-reported or invoice-reconciled evidence status. `ReconciliationCase` records mismatches and explicit adjustments. The existing upstream pricing evidence may seed a draft, but nullable `OicUpstreamPricingEvidence` does not prove authoritative invoice cost.

## OIU and money

OIU is nonnegative fixed-point decimal (proposed scale 6, persist exact decimal; overflow rejects), normalized resource consumption under an immutable `OiuPolicyRevision`. The policy maps typed provider-independent dimensions (input/output/cached tokens, billed image/audio/video units, requests, tools, storage as actually reported) to weighted OIU, with explicit unit conversion, minimum increment, round-half-even once per posting, and a policy-defined treatment of missing dimensions. Unreported hidden reasoning tokens are never inferred. Preserve raw provider payload allowlist and normalized dimension values. OIU posts pin policy revision, inputs, output and derivation digest. A new policy does not restate history.

Provider cost uses separate immutable effective-dated pricing revisions and a per-assessment rate snapshot; actual invoice truth, provider-reported charge, deterministic catalog estimate and unknown are distinct evidence levels. Provider price can have arbitrary typed billing dimensions, not only tokens. Currency is ISO code; arithmetic is decimal and any conversion pins an FX source/time if later authorized. Customer price/value are separate future domains and never inferred from cost or OIU. No external billing capability is authorized by this architecture.

## Deterministic entitlement and quota

Resolution at admission: authenticate principal → validate application/tenant grant and resource visibility → pin selected model binding and current immutable policy revisions → collect active app/tenant plan assignment and explicit scoped override → deny on conflicting deny rule → allow only if a matching grant exists → apply **every matching hard-limit bucket atomically**; soft limits emit warning only. Override requires separate privilege, expiry, reason and audit; it cannot override security scope. No plan/grant means deny for metered resource. Plan changes affect new admissions; in-flight reservations retain pinned policy. Windows use UTC half-open `[start,end)` boundaries; fixed calendar and rolling windows are different explicit policy types. No unlimited default. Exact resolution and reservation sizing are in the [v1.0 protocol](../../oic-6-9/oic-6/12_ADMISSION_LEDGER_AND_RECONCILIATION.md).

Hard quota is enforced in PostgreSQL in one serializable transaction or row-lock equivalent: unique invocation/admission key; lock balance row(s) in deterministic order; verify `consumed + reserved + requested <= limit`; write reserve posting; update projection; commit. A concurrent request must observe the committed reserve or retry serialization with bounded backoff. No Redis counter is authoritative. Reservation amount is upper-bound call budget; if a provider has no enforceable upper bound, hard quota admission denies or uses a policy-defined conservative cap and server-side output limit. Long calls need expiration with fenced lease/heartbeat, not blind release while the call may still run. Capture provider attempt identity before outbound request to avoid untracked retries. A replay of the same key and payload returns the same admission/result; same key with different hash conflicts. Streaming requires a new retry/continuation contract because current runtime rejects streaming idempotency.

On completion, atomically post observed consumption, release unused reserve and update balance. If observed usage exceeds reserve, record debt/overrun and block further admission pending reconciliation; never truncate actual usage. If provider call fails before dispatch, release. If dispatch may have occurred and usage is unknown, keep a bounded liability hold and `PENDING_RECONCILIATION`; do not post zero. Reconcile against provider report/invoice via append-only adjustment or reversal with source reference, approval threshold and audit. Crash recovery finds expired fenced reservations, probes known attempt state and only releases when no provider call can still charge. Database outage fails closed for hard quota; cache/Redis loss does not change enforcement. Provider timeout and network ambiguity remain unknown until evidence arrives.

## Attribution, API, UI, operations

Every event pins application/tenant/principal, invocation/trace, provider connection, upstream model, model revision/variant/binding, profile revision, policy revisions and provider attempt; nullable IDs carry explicit resolution status. Aggregate read models are materialized from ledger, not mutable economic truth. API families: `POST /usage/admissions`, `POST /usage/attempts`, `POST /usage/reconcile` (internal machine boundary); scoped `GET /usage`, `/quotas`, `/plans`, `/costs`, and privileged revision/assignment/override commands. Exact HTTP shape is packet work, but fields/status/errors (`DENIED`, `EXHAUSTED`, `PENDING_USAGE`, `UNKNOWN_COST`, `CONFLICT`) are contract requirements. Client cannot self-report authoritative consumption or bypass admission. BFF passes existing session and machine credential boundaries; no raw provider credential in browser.

Console uses canonical Interface pickers/tables/Inspectors and Instrument displays only source-backed measures. Show raw usage, OIU, cost evidence level, reservation, remaining quota and reconciliations as separate fields; unknown is explicit. Operators can inspect policy revision and posting chain, resolve reconciliation with permissions, and never silently edit historical posts. Monitoring: admission denials, balance drift, unclosed reservations, unknown usage age, delayed provider receipts, invoice mismatch, worker backlog, plan expiry and audit write failure. Rollout: shadow-meter first with no hard enforcement, reconcile against traces/provider evidence, then canary hard limits per scope, then wider enablement after concurrency/rollback gates. Migration may backfill clearly labeled `HISTORICAL_UNVERIFIED` aggregates, never fabricated authoritative usage.
